# mruby/c UX authoring

When the product embeds mruby/c (8-bit AVR, Zephyr, nRF Connect,
Emscripten, ESP32, RP2040 and friends), UX logic that runs on-device —
state feedback, LED/buzzer cues, interaction loops — is written as plain
`.rb` files under `ux/` and handed to firmware through a manifest.

## Workflow

1. Write the UX logic in `ux/<feature>.rb` — plain mruby/c Ruby (see the
   limits below). `*.ux.rb` DSL files are contract sources, not VM code;
   the manifest never lists them.
2. Emit the manifest:

   ```bash
   python -m ux_creator mruby-manifest --dir ux --product <name>
   # writes ux/<name>.mruby-manifest.json
   ```

3. Hand it to firmware: the firmware contract pins the manifest with
   `mrubyc.ux_manifest` (path + sha256) and lists each `.rb` in
   `mrubyc.sources`. Re-run the command after every `.rb` edit — a stale
   hash fails both gates.
4. Verify locally before handing off:

   ```bash
   python -m ux_creator mruby-manifest --dir ux --product <name> --check
   python -m ux_creator mruby-check ux/app.rb   # mrbc -c syntax gate
   ```

## Manifest contents

```json
{
  "artifact_kind": "mruby_manifest",
  "product": "kettle",
  "files": [{"file": "ux/app.rb", "sha256": "<64-hex>"}],
  "requires": {"float": 1, "math": false, "string": true, "utf8": false, "tick": true}
}
```

`requires` is auto-detected from the sources and must fit the VM flags
the firmware contract configures:

| requires | set when | firmware flag it needs |
| --- | --- | --- |
| `float` (0-2) | float literals, `.to_f`, `Float` | `use_float >= level` |
| `math` | `Math.` calls | `use_math` |
| `string` | string ops/interpolation | `use_string` |
| `utf8` | non-ASCII source | `use_utf8` |
| `tick` | `VM.tick`, `sleep`, `sleep_ms`, `VM.sleep` | `no_timer` must be false |

`--float 2` raises the declared float level when the UX needs double
precision (e.g. `Math.exp` results consumed by a gauge); the default
is 1. Keep it honest — a higher level grows VM RAM/flash.

## mruby/c Ruby subset

- mrbc 4.0 bytecode (`RITE0400`); no gems, no `require`, no native calls.
- Prefer integers and small arrays; the heap is `memory_size` bytes.
- `String` exists only when `use_string` is on — flag interpolation
  (`"#{x}"`) counts as String use and is detected.
- `Float` needs `use_float >= 1`; math functions need `use_math`.
- Cooperative scheduling: `VM.tick`/`sleep` yields to the VM loop; they
  need the tick timer (`no_timer: false`).
- Keep classes small and files focused — `classes:` in the manifest is
  informational for the VM's class table.

## Failure modes (fail-closed)

- `.rb` edited after the manifest was written → sha mismatch → re-run
  the command.
- New `*.rb` file in `ux/` not listed → gate fails → re-run the command.
- `requires` under-declared (e.g. code uses `Float` with `float: 0`) →
  gate fails → fix the source or raise the declaration.
- Firmware-side `fw.mrubyc` re-runs `mrbc -c` and byte-compares the
  generated bytecode — a manifest alone never ships.

## Device API specs (`*.mruby-api.json`)

When the product needs device-specific classes/methods (the OpenBlink
style: `LED.set(part:, state:)`, `Sample.new.read(ch)`), UX owns the API
surface — it is user experience. Author `api/<name>.mruby-api.json`
(artifact_kind `mruby_api`, schema_version 1):

```json
{
  "product": "<name>",
  "symbols": [{"name": "led1", "const": "kFwHwLed1"}],
  "system_task": {"vm_id": 1},
  "expert_define": "FW_DEBUG_API",
  "classes": [{
    "name": "LED", "doc": "...",
    "methods": [{
      "name": "set", "doc": "...",
      "kwargs": [{"name": "part", "type": "symbol", "enum": ["led1"]},
                  {"name": "state", "type": "bool", "required": false, "default": false}],
      "returns": {"type": "bool"}, "handler": "fw_hw_led_set"
    }]
  }]
}
```

Method shape: `params` positional, `kwargs` keyword (symbol params carry
`enum` of declared symbols; `string`/`array<int>` need `max_len`),
`rest_kwargs` for `**rest`, `block: required|optional` for callbacks,
`access: system_task|expert`, `arg_errors: raise|silent`,
`returns.type` ∈ nil/int/float/bool/symbol/string/array\<T\> (buffers
need `cap`), `instance` for data-carrying classes (data_size +
constructor/destructor handlers), `constants` for `CLASS::NAME`.

Ruby-ness is gated — `python -m ux_creator mruby-api <spec> --check`
fails on: missing doc lines, non-snake_case names, `?` methods not
returning bool, `get_`/`set_` prefixes, >3 positional args, `on_*`
methods without a block, symbol params without `enum`, class names
colliding with classes defined in the ux `*.rb` sources, and `*.rb`
call sites (`LED.foo`) the spec does not declare — including undeclared
`:symbol` arguments. Without `--check` the command renders
`<name>.mruby-api.md`, the user-facing API reference.

The manifest now lists the classes ux `*.rb` files define, so firmware
can reject collisions between Ruby-defined and API-declared classes.

Hand-off: firmware pins the spec under `mrubyc.device_api`
{spec, sha256, handlers_header} and generates `fw_api_*.{c,h}`; the
`.rb` UX logic calls the API through the generated bindings.
